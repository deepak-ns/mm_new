# Starbucks MDP Offer Optimizer

## 1. Project Summary

This project builds a decision-support system for choosing which Starbucks offer should be sent to each customer segment. The main idea is to model offer selection as a Markov Decision Process (MDP), where customers move between business states such as High Value, Offer Responsive, Low Value, At Risk, and Inactive.

The goal is not only to maximize immediate transaction revenue, but also to choose actions that improve long-term customer value. For example, sending a discount may cost money today, but if it moves an At Risk customer into a more active state, it may be profitable over time.

The project compares two policies:

1. A baseline rule-based policy that represents a simple business heuristic.
2. An MDP optimal policy learned using Value Iteration.

The Streamlit dashboard shows KPIs, revenue simulation, state distributions, policy decisions, transition probabilities, reward matrix, and raw simulation data.

## 2. Problem Statement

Starbucks has different types of promotional offers:

- `no_offer`: Do not send any offer.
- `bogo`: Buy-one-get-one style offer.
- `discount`: Discount offer.
- `informational`: Low-cost informational message.

The business question is:

> For each type of customer, which offer should Starbucks send so that long-term net revenue and customer retention improve?

A naive method would send offers based only on current customer type. This project improves on that by considering:

- Current customer state.
- Cost of each action.
- Probability of moving to a better or worse future state.
- Long-term value of future customer behavior.

## 3. Dataset Used

The project uses a synthetic Starbucks-like dataset generated by `generate_data.py`. It follows the structure of the well-known Starbucks offer dataset:

- `portfolio.json`: Offer catalog.
- `profile.json`: Customer demographic data.
- `transcript.json`: Event log of transactions and offer interactions.

The generated event log contains:

- `offer received`
- `offer viewed`
- `offer completed`
- `transaction`

The data is synthetic, so it is not a real Starbucks business result. It is designed to demonstrate MDP-based decision making in a realistic marketing setting.

## 4. Project Pipeline

The full pipeline is:

1. Generate or load data.
2. Flatten transcript event values.
3. Merge offer data, customer profile data, and event logs.
4. Engineer user-level features.
5. Assign each customer to a discrete MDP state.
6. Extract observed state-action-next-state transitions.
7. Build the transition probability matrix.
8. Build the reward matrix.
9. Solve the MDP using Value Iteration.
10. Simulate baseline and MDP policies over 90 days.
11. Compare KPIs in the dashboard.

## 6. Methodology

### 6.1 Feature Engineering

The raw transcript is converted into one row per user. The main features are:

| Feature | Meaning |

| `recency` | Days since last activity |
| `income` | Customer income from profile data |

These features are used to classify each customer into a state.

The model uses 5 discrete states:

| State Index | State Name | Meaning |

| 1 | Offer Responsive | Strong offer viewing or completion behavior |
| 2 | Low Value | Low spend and low activity but not inactive |
| 3 | At Risk | Previously active but recent activity is low |
| 4 | Inactive | Very low transaction and offer activity |

## 7. MDP Mathematical Formulation

An MDP is defined by:

```text
MDP = (S, A, P, R, gamma)
```

Where:

- `S` is the set of states.
- `A` is the set of actions.
- `P(s' | s, a)` is the probability of moving to next state `s'` after taking action `a` in state `s`.
- `R(s, a)` is the immediate reward for taking action `a` in state `s`.
- `gamma` is the discount factor.

In this project:

```text
S = {High Value, Offer Responsive, Low Value, At Risk, Inactive}
A = {no_offer, bogo, discount, informational}
gamma = 0.95
```

The value function is:

```text
V(s) = expected long-term discounted reward starting from state s
```

The Bellman optimality equation is:

```text
V*(s) = max_a [ R(s, a) + gamma * sum_s' P(s' | s, a) * V*(s') ]
```

The action-value function is:

```text
Q(s, a) = R(s, a) + gamma * sum_s' P(s' | s, a) * V(s')
```

The optimal policy is:

```text
pi*(s) = argmax_a Q(s, a)
```

In simple words, the model asks:

> If the customer is in this state, which action gives the best immediate reward plus the best expected future value?

## 8. Transition Matrix Construction

The transition matrix is stored as:

```text
P[s, a, s']
```

Its shape is:

```text
5 states x 4 actions x 5 next states
```

So each row answers:

```text
Given current state s and action a, what is the probability of ending in each next state s'?
```

### 8.1 How Transitions Are Extracted

The code loops through each customer and sorts their events by time.

For every `offer received` event:

1. The current state is taken from the customer's engineered features.
2. The offer type is mapped to an action:
   - `bogo` -> action 1
   - `discount` -> action 2
   - `informational` -> action 3
3. Events after that offer are examined.
4. A temporary "future behavior" profile is created using:
   - transactions after the offer,
   - offer completions after the offer,
   - number of later received offers,
   - part of the user's existing history.
5. That temporary profile is classified again using the same state rules.
6. The tuple `(state, action, next_state)` is recorded.

If a customer has no offer events, the code adds a self-transition:

```text
(current_state, no_offer, current_state)
```

For the current dataset, the code extracted:

```text
8,674 state-action-next-state transitions
```

### 8.2 How Probabilities Are Deduced

For each combination of state and action, the code counts how many times each next state occurred:

```text
count[s, a, s'] = number of observed transitions from s to s' using action a
```

The empirical probability would be:

```text
P_empirical(s' | s, a) = count[s, a, s'] / sum_k count[s, a, k]
```

However, some state-action combinations may have very few observations. To avoid zero-probability problems, the project uses smoothing with a domain prior.

The final formula is:

```text
posterior_count[s, a, s'] = observed_count[s, a, s'] + alpha * prior[s, a, s']

P(s' | s, a) = posterior_count[s, a, s'] / sum_k posterior_count[s, a, k]
```

In the code:

```text
alpha = 5.0
```

This is similar to Laplace/Bayesian smoothing, except the prior is business-informed rather than uniform.

### 8.3 Why Use a Domain Prior?

Without smoothing:

- Rare transitions could get probability zero.
- The MDP may overfit to random noise.
- Some actions may appear impossible in states where the data is sparse.

The domain prior encodes reasonable business assumptions. For example:

- High Value customers are likely to remain High Value.
- Inactive customers often remain Inactive if no strong offer is sent.
- Offer Responsive customers can improve with `bogo`.
- At Risk customers may decline without intervention.

The observed data still matters. The prior only stabilizes the transition estimates.

## 9. Reward Function

The reward matrix is:

```text
R[s, a]
```

Its shape is:

```text
5 states x 4 actions
```

The project uses this reward formula:

```text
R(s, a) =
    base_revenue(s)
  + completion_probability(s, a) * completion_bonus(a)
  - action_cost(a)
  - spam_penalty(s, a)
```

### 9.1 Reward Components

#### Base Revenue

This represents expected transaction value from each customer state.

| State | Base Revenue |
|---|---:|
| High Value | 12.0 |
| Offer Responsive | 6.0 |
| Low Value | 3.5 |
| At Risk | 5.0 |
| Inactive | 1.0 |

#### Action Cost

| Action | Cost |
|---|---:|
| `no_offer` | 0.0 |
| `bogo` | 2.0 |
| `discount` | 1.5 |
| `informational` | 0.5 |

#### Completion Bonus

| Action | Completion Bonus |
|---|---:|
| `no_offer` | 0.0 |
| `bogo` | 4.0 |
| `discount` | 2.5 |
| `informational` | 0.5 |

#### Spam Penalty

The spam penalty discourages sending costly or irrelevant offers to customers who are unlikely to respond, especially Low Value and Inactive customers.

For example:

- Sending `bogo` to an Inactive user has a higher penalty.
- Sending `informational` to an Inactive user has a smaller penalty.
- High Value and Offer Responsive users have no spam penalty.

### 9.2 Why Reward Is Not Just Revenue

If reward only counted transaction revenue, the model might send too many offers. The reward function includes costs and penalties so the policy learns that:

- Some offers are too expensive for certain customers.
- Not sending an offer can be optimal.
- Low-cost informational actions can be useful for weak segments.
- Long-term state improvement matters.

## 10. Baseline Policy

The baseline policy is a simple deterministic business rule:

| State | Baseline Action | Reason |
|---|---|---|
| High Value | `bogo` | Reward loyal high spenders and encourage continued spend |
| Offer Responsive | `bogo` | They engage with offers, so a strong offer is likely to work |
| Low Value | `discount` | Use a lower-cost incentive to increase activity |
| At Risk | `discount` | Try to reactivate with a moderate incentive |
| Inactive | `informational` | Avoid expensive rewards; send a low-cost reminder |

This baseline is not learned from optimization. It is a reasonable heuristic used for comparison.

## 11. MDP Optimal Policy

The MDP policy is learned using Value Iteration. For each state, it chooses the action with the maximum expected long-term value.

Current learned policy at `gamma = 0.95`:

| State | Baseline Action | MDP Action | Value V*(s) |
|---|---|---|---:|
| High Value | `bogo` | `no_offer` | 126.490 |
| Offer Responsive | `bogo` | `bogo` | 99.953 |
| Low Value | `discount` | `informational` | 87.581 |
| At Risk | `discount` | `informational` | 88.201 |
| Inactive | `informational` | `discount` | 67.978 |

### 11.1 Why the MDP Chooses These Actions

#### High Value -> `no_offer`

High Value customers already have high transaction probability and high base revenue. The MDP may learn that sending a costly offer is unnecessary because these customers are likely to buy anyway. Therefore, `no_offer` preserves revenue without adding offer cost.

#### Offer Responsive -> `bogo`

Offer Responsive customers engage strongly with promotions. The completion probability for `bogo` is high, and the transition model suggests that strong offers can keep or improve their state. So `bogo` remains optimal.

#### Low Value -> `informational`

Low Value customers may not justify costly incentives. The MDP prefers a low-cost informational action because it has small cost and avoids over-spending on customers with lower immediate expected value.

#### At Risk -> `informational`

At Risk users need re-engagement, but discounts may not always pay off after cost and spam penalty. Informational messages provide a cheaper intervention while still offering some chance of state improvement.

#### Inactive -> `discount`

Inactive customers have very low base revenue. The MDP learns that a discount may be worth the cost if it increases the chance of moving them out of Inactive. This is a long-term decision, not just an immediate reward decision.

## 12. Value Iteration

The solver starts with:

```text
V(s) = 0 for all states
```

Then repeatedly updates:

```text
Q(s, a) = R(s, a) + gamma * sum_s' P(s' | s, a) * V(s')
V(s) = max_a Q(s, a)
```

The process stops when:

```text
max_s |V_new(s) - V_old(s)| < epsilon
```

In the current run:

```text
epsilon = 1e-6
gamma = 0.95
iterations = 301
final delta = 9.55e-07
```

This means the values have stabilized and the policy is considered converged.

## 13. Simulation Method

After learning the optimal policy, the project simulates both policies for the same initial customer cohort over 90 days.

For each day and each user:

1. Read current state.
2. Select action from the policy.
3. Simulate whether the user transacts.
4. Simulate transaction amount based on state.
5. Simulate whether the offer is completed.
6. Compute reward.
7. Sample the next state using `P[s, a, :]`.
8. Store the result.

The simulator is Monte Carlo based, meaning it uses random sampling from the transition probabilities and transaction distributions.

## 15. Important Assumptions

### Data Assumptions

- The dataset is synthetic and designed to behave like a Starbucks offer dataset.
- Customer behavior in the simulation is assumed to follow the generated event patterns.
- Income influences synthetic spending behavior.
- Events over 30 days are used to infer customer states and transition patterns.

### State Assumptions

- Five states are enough to summarize customer behavior.
- RFM-style features capture the most important differences between customers.
- Rule-based state classification is interpretable and suitable for presentation.

### Transition Assumptions

- Future customer state can be estimated from activity after offer events.
- Sparse observations should be smoothed with a domain prior.
- The transition probability depends only on current state and action, not the full customer history. This is the Markov assumption.

### Reward Assumptions

- Base revenue by state approximates expected spending.
- Offer costs represent business cost of promotions.
- Completion bonus represents business benefit of successful offer redemption.
- Spam penalty discourages over-targeting weak or inactive users.

### Simulation Assumptions

- A fixed policy is used throughout the simulation.
- Daily customer transitions are sampled from the learned transition matrix.
- Transaction probability and amount depend on current state.
- Results may vary slightly because simulation uses randomness.

## 16. Limitations

- The data is synthetic, not real Starbucks production data.
- The state classifier is rule-based, not learned by clustering or supervised learning.
- The transition model is approximate because real causality cannot be proven from synthetic event logs.
- The reward values are manually designed business assumptions.
- The model uses a stationary MDP, meaning transition probabilities do not change over time.
- The policy is state-level, not fully personalized at individual-user level.

## 17. Why MDP Is Suitable Here

An MDP is useful because offer decisions affect future customer behavior. A simple one-step model would only ask:

```text
Which offer gives the highest immediate revenue?
```

The MDP asks:

```text
Which offer gives the best immediate reward plus future customer value?
```

This is important in marketing because:

- Giving too many offers can reduce profit.
- Some customers need reactivation.
- Some customers buy without offers.
- A costly action today may improve future state.
- The best action depends on both present and future outcomes.

## 18. Questions Your Teacher May Ask

### What is the objective of the project?

The objective is to learn an optimal offer policy that maximizes long-term net reward for different customer states, while comparing it against a simple rule-based baseline policy.

### Why did you use an MDP?

Because offer decisions are sequential. The effect of an offer is not limited to immediate revenue; it can move customers into better or worse future states. MDPs are designed for this kind of long-term decision making.

### What are states?

States are customer segments based on spending, transaction frequency, offer engagement, completion rate, and recency. The five states are High Value, Offer Responsive, Low Value, At Risk, and Inactive.

### What are actions?

Actions are the possible decisions Starbucks can take for a customer: no offer, BOGO, discount, or informational message.

### How did you calculate the transition matrix?

The event log is scanned for offer events. For each offer received, the current customer state and action are recorded. Then later activity after the offer is used to estimate the next state. These `(state, action, next_state)` tuples are counted. Counts are combined with a domain prior using smoothing, then normalized to probabilities.

### Why did you use smoothing?

Some state-action pairs may have few observations. Smoothing avoids zero probabilities and makes the transition matrix more stable.

### What is the reward function?

The reward function combines expected base revenue, offer completion benefit, action cost, and spam penalty:

```text
R(s, a) = base_revenue(s)
        + completion_probability(s, a) * completion_bonus(a)
        - action_cost(a)
        - spam_penalty(s, a)
```

### How did you decide baseline actions?

The baseline actions are manually chosen business rules. High Value and Offer Responsive users receive BOGO, Low Value and At Risk users receive discounts, and Inactive users receive informational messages. This represents a reasonable non-optimized marketing strategy.

### How are MDP actions decided?

MDP actions are chosen by Value Iteration. For each state, the algorithm calculates the expected long-term value of every action and selects the action with the highest value.

### Why does the MDP sometimes choose `no_offer`?

Because offers have costs. If a customer is likely to purchase anyway, sending an offer may reduce profit. For High Value customers, `no_offer` can be better because it avoids unnecessary cost.

### Why is offer completion lower for the MDP policy?

The MDP is not optimizing completion rate alone. It optimizes long-term net reward. It may send fewer costly offers, which can reduce completion rate but increase net revenue and retention.

### What is gamma?

`gamma` is the discount factor. It controls how much the model values future rewards. A high gamma such as 0.95 means the model strongly considers long-term outcomes.

### What does convergence mean?

Convergence means the value function has stopped changing significantly. In this project, Value Iteration stops when the maximum value change is below `1e-6`.

### What is the Markov assumption?

The Markov assumption means the next state depends only on the current state and action, not the full previous history. The history is summarized into the current state.
